# SOLUTION — Lab 03: Compliance Audit and Documentation

Reference solution for
[lab-03-compliance-audit.md](https://github.com/ai-infra-curriculum/ai-infra-senior-engineer-learning/blob/main/lessons/mod-209-security-compliance/exercises/lab-03-compliance-audit.md).

Engineer-tier evidence-collection scripts are the same as
`engineer-solutions/mod-109 ex-07/08`; the senior
responsibility here is to produce audit artifacts that a
third-party assessor accepts on first pass — a mapped control
set, evidence that was generated by the pipeline (not
assembled the night before), and a written story that ties
findings to risk.

## 1. Solution overview

An audit is a question about *evidence*: for each control the
organisation claims, does the artifact exist, is it current,
and is it tied to the system it governs? The AI-specific
framings used in this reference are:

- **NIST AI Risk Management Framework 1.0** (AI RMF) —
  Govern / Map / Measure / Manage functions; the top-level
  structure an auditor expects to see
  ([NIST — AI RMF](https://www.nist.gov/itl/ai-risk-management-framework);
  [NIST.AI.100-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.100-1.pdf)).
- **NIST AI 600-1 — Generative AI Profile** (July 2024)
  — AI RMF subcategories specific to generative AI systems,
  and recommended actions
  ([NIST.AI.600-1](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)).
- **OWASP Machine Learning Security Top 10** — threat
  framing for ML-specific risks the audit must show are
  addressed
  ([OWASP ML Top 10](https://owasp.org/www-project-machine-learning-security-top-10/)).
- **MITRE ATLAS** — adversary-technique catalogue that
  anchors the "what are we defending against" half of the
  narrative ([MITRE ATLAS](https://atlas.mitre.org/)).

Senior additions on top of "a binder of screenshots":

- **Control-to-evidence map is the authoritative artifact.**
  The narrative, the screenshots, and the policy text are
  attachments; the mapping is the index.
- **Evidence is produced by the system, not by the auditor.**
  A Terraform plan output, a Kyverno admission log, an Argo
  CD sync record — all are first-class evidence because
  they are tamper-evident and continuous. A screenshot of a
  dashboard is a last resort.
- **Findings get a risk rating, an owner, and a
  remediation path**, not just a status column.

## 2. Worked answer or implementation

### 2a. Audit scope statement (first deliverable)

A one-page scope document a third party will read before any
evidence is produced. It fixes what is in and out — otherwise
every question balloons.

> **Scope.** This audit covers the production ML inference
> platform ("acme-mlp") operated by the ML Platform team: the
> inference-serving cluster (`mlp-prod-use1`), the model
> registry (`registry.acme.com`), and the training pipeline
> that produces the artifacts served in production
> (`mlp-train-use1`). It does not cover dataset acquisition
> upstream of the Feature Store, user-application logic, or
> the shared identity provider (audited separately).
>
> **Audit window.** Controls assessed as of 2026-11-01. Evidence
> continuous back to 2026-05-01 (minimum 6 months of operation
> required for SOC 2 Type II-style assertions).
>
> **Framework.** NIST AI RMF 1.0 as the top-level structure,
> with AI 600-1 subcategories applied for generative-AI
> components (if any). OWASP ML Top 10 used as threat
> cross-reference for ML-specific risks. MITRE ATLAS used as
> adversary-technique reference.

### 2b. Control-to-evidence map (the core artifact)

A table keyed by framework subcategory. The reference
excerpt below shows the shape and is non-exhaustive.

| Control ID | Framework reference | Statement | Evidence artifact | Source system | Collection frequency | Owner |
|---|---|---|---|---|---|---|
| AC-01 | AI RMF **GOVERN 1.1** | Legal and regulatory requirements are documented and reviewed | `compliance/policy-register.md` + review PRs | Git | Quarterly | Legal |
| AC-02 | AI RMF **GOVERN 1.4** | Roles and responsibilities for AI risk are documented | `compliance/raci.md` | Git | Per org change | VP Eng |
| AC-03 | AI RMF **MAP 2.1** | AI system categorisation documented per use case | `registry/<model>/model-card.md` | Model registry | Per release | Model owner |
| AC-04 | AI RMF **MEASURE 2.6** | Monitoring for degradation and drift is in place | Grafana dashboard JSON + Prometheus rules in Git | Grafana / Prom | Continuous | SRE |
| AC-05 | AI RMF **MANAGE 2.4** | Incident response plan covers AI-specific incidents | `runbooks/ai-incident.md` + quarterly tabletop record | Confluence / Git | Quarterly tabletop | Security |
| AC-06 | AI 600-1 **GV-6.1-002** | Third-party AI components are assessed and tracked | SBOM per image (CycloneDX) + review ticket | Cosign / registry | Per release | Platform |
| AC-07 | OWASP **ML06** | Image provenance verified before admission | Kyverno audit log entries for `verify-image-signatures` | Kyverno / SIEM | Continuous | Platform |
| AC-08 | OWASP **ML02** | Data poisoning defences: training data lineage captured | DVC / MLMD lineage record | Pipeline | Per training run | ML Platform |
| AC-09 | ATLAS **TA0043 Resource Development** | Base images come from approved sources | Admission policy + registry allow-list | Kyverno / registry | Continuous | Platform |
| AC-10 | AI RMF **MANAGE 4.3** | Periodic review of controls occurs | PR history of this document | Git | Quarterly | Security |

Each row has a *single* owner. A control with two owners is a
control with none.

### 2c. Evidence samples — what each artifact looks like

**AC-04 (monitoring continuity).** The evidence is the *source
of the metric*, not a screenshot of a grafana panel.

```
# Prometheus alert rule, stored at policies/prom/drift.yaml
- alert: ModelPredictionDriftHigh
  expr: |
    avg_over_time(model_prediction_drift_score{env="prod"}[30m]) > 0.3
  for: 30m
  labels: { severity: warning, control_id: AC-04 }
  annotations:
    summary: "Drift score > 0.3 for 30m on {{ $labels.model }}"
    runbook: https://runbooks.acme.com/ai-drift
```

The `control_id` label is the audit hook — every control-relevant
alert carries its control ID so a SIEM query enumerates evidence
without a human curating it.

**AC-07 (image signature verification).** Evidence is a Kyverno
policy report plus the admission log stream:

```bash
kubectl get policyreports -A -l control.acme.com/id=AC-07 \
  -o jsonpath='{.items[?(@.summary.fail>0)]}' | jq .
```

If this returns anything, there is a signed-image violation in
the audit window. The absence is the control.

**AC-08 (data lineage).** Evidence is the training-run record
in the pipeline metadata store (MLMD / MLflow):

```
training_run:
  id: 2026-10-28-abc123
  dataset:
    name: customer-support-v3
    sha256: a4f...
    classification: PII-allowed
    source_commit: data-pipeline@v1.14.2
  model:
    sha256: cafe...
    registry_uri: oci://registry.acme.com/models/support-llm@sha256:cafe...
  signed_by: cosign-key-id-prod-1
```

### 2d. Model cards as the Map-function artifact

Each model served in production has a model card
([Model Cards for Model Reporting (Mitchell et al.)](https://arxiv.org/abs/1810.03993))
checked into the registry repo. The card is the artifact an
auditor reads to understand what the model is and the
constraints on its use — it covers AI RMF **MAP 1–5** in one
document.

Minimum fields the reference requires:

- Intended use, out-of-scope use, foreseeable misuse.
- Training data: source, classification, consent basis,
  cut-off date.
- Evaluation metrics: on which benchmarks, on which slices,
  measured when.
- Known limitations and failure modes.
- Responsible-use guidance for downstream teams.
- Owner, contact, next review date.

For generative-AI systems, the card additionally covers the
items AI 600-1 flags as distinctively generative:
confabulation risk, data privacy in prompts, content
provenance, and information security
([AI 600-1 — Suggested Actions, generative-AI-specific
subcategories](https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf)).

### 2e. Findings, risk rating, and remediation

Audit findings are written in a consistent shape so they are
tractable to track and close:

```
Finding: F-2026-11-03
  Control: AC-07 (OWASP ML06 — supply chain)
  Observation: 3 of 142 deployed pods in mlp-prod-use1 run
    images from the registry path ghcr.io/acme/experimental/*
    which is not in the Kyverno allow-list. The verify-image-
    signatures policy is in Audit mode (not Enforce) for that
    path.
  Impact: a typosquatted or compromised image could be
    admitted; blast radius is the inference namespace.
  Likelihood: Low (allow-list bypass requires cluster-admin)
  Severity: High (model integrity, ML06)
  Risk rating: Medium
  Owner: ML Platform
  Remediation:
    1. Move verify-image-signatures to Enforce on the
       experimental path (PR #882).
    2. Migrate the 3 pods to signed images in the primary
       registry path.
  Due: 2026-12-01
  Verification: Kyverno policy report shows 0 Fail in the
    week before close.
```

Severity × likelihood → risk rating is a documented matrix in
`compliance/risk-rating.md` (3×3 or 5×5 — the matrix itself
matters less than the fact that it is written down and used
consistently).

### 2f. The written narrative

Auditors read the narrative first and the evidence second. A
reference section-structure:

1. **System description.** What acme-mlp does, who uses it,
   what data it touches.
2. **Framework alignment.** Which framework, which
   subcategories in scope, which out.
3. **Control environment.** How the pipeline, the cluster,
   and the registry enforce the controls structurally.
4. **Findings and remediations.** The table from §2e,
   summarised.
5. **Residual risk statement.** The risks the organisation
   has accepted and why.
6. **Next review date.** AI RMF MANAGE expects controls to
   be reviewed over time; the next review is scheduled, not
   "when we get to it".

### 2g. Automation: audit is a continuous job, not a sprint

A `compliance-evidence` CI job runs nightly and produces a
dated manifest of control status:

```bash
# compliance/collect.sh (sketch)
TODAY=$(date -u +%Y-%m-%d)
mkdir -p "artifacts/$TODAY"

# AC-04
kubectl get prometheusrule -A -o yaml \
  | yq '.items[] | select(.metadata.labels["control.acme.com/id"]=="AC-04")' \
  > "artifacts/$TODAY/ac-04-rules.yaml"

# AC-07
kubectl get policyreports -A -l control.acme.com/id=AC-07 -o yaml \
  > "artifacts/$TODAY/ac-07-policyreports.yaml"

# AC-08
./pipeline/mlflow-export --since -24h \
  > "artifacts/$TODAY/ac-08-lineage.jsonl"
```

Artifacts land in an immutable (object-lock) bucket with
retention aligned to the audit window (minimum 1 year for
most frames). At audit time, the assessor reads from the
bucket; nothing is hand-assembled.

## 3. Validation steps

1. The control-to-evidence map is complete — every row has
   `evidence artifact`, `source system`, and `owner` filled.
2. For a randomly chosen row, the evidence can be retrieved
   from the source system *as of a chosen prior date*
   (that's the "continuous" claim: a point in the past is
   recoverable, not just today).
3. Model cards exist for every model listed in
   `registry.acme.com` under a `production` tag; each card
   covers all required fields in §2d.
4. The nightly `compliance-evidence` CI job has run every
   day for the audit window (no gaps > 1 day) and has
   written to the immutable bucket.
5. At least one finding has been raised, remediated, and
   closed inside the audit window — showing the loop works.
6. The quarterly tabletop record for AC-05 is present with
   participants and date.
7. The risk-rating matrix in `compliance/risk-rating.md` is
   referenced by every finding's rating line.

## 4. Rubric / review checklist

| # | Check | Weight |
|---|---|---|
| R1 | Written scope statement fixes what is in and out of audit, with dates and systems | 10 |
| R2 | Control-to-evidence map keyed by AI RMF (and AI 600-1 for genAI) subcategory IDs, with single owner per row | 15 |
| R3 | Evidence is pipeline-produced (logs, policy reports, lineage records) — not hand-captured screenshots — for ≥80% of controls | 15 |
| R4 | Every production model has a model card covering intended use, training-data source and classification, evaluation, limitations, owner | 10 |
| R5 | OWASP ML Top 10 and MITRE ATLAS are explicitly referenced in control rationales where ML-specific | 10 |
| R6 | Findings use a consistent template with severity, likelihood, risk rating, owner, due date, and verification | 10 |
| R7 | A documented risk-rating matrix exists and is referenced by findings | 5 |
| R8 | Evidence-collection is automated; a daily artifact exists for the entire audit window in an immutable store | 15 |
| R9 | Narrative section ends with a residual-risk statement and a next-review date | 10 |

Pass threshold: **80/100**. R2, R3, and R8 are must-haves —
a compliance exercise without a mapping, without system-produced
evidence, or without continuity over time is a point-in-time
spreadsheet, not an auditable control environment.

## 5. Common mistakes

1. **A binder of screenshots.** Point-in-time, not reproducible,
   not continuous. Screenshots are acceptable only as a
   last-resort attachment.
2. **Mapping to a framework without reading it.** Citing "NIST
   AI RMF" with no subcategory ID is a smell — the framework is
   organised by GV/MP/MS/MG subcategories for a reason.
3. **Model cards written at audit time.** A card produced two
   weeks before the assessor arrives does not reflect the
   system as it ran for the preceding year. Cards live in the
   registry alongside the model and are versioned with it.
4. **Severity without likelihood.** "High severity" findings
   with no likelihood estimate produce a remediation backlog
   nobody can prioritise. Use the matrix.
5. **One-off evidence collection.** A script that runs once
   before the audit; nobody notices when it breaks the day
   after. Continuous, dated, and immutable.
6. **Audit log retention shorter than the audit window.** If
   logs rotate at 30 days and the window is 6 months, the
   evidence for months 2–5 does not exist. Set retention
   deliberately.
7. **Control owner = "the team".** Teams don't sign; people
   do. Name a role (preferably title, not person) that is
   accountable.
8. **Treating MITRE ATLAS and OWASP ML Top 10 as
   interchangeable.** They are not. ATLAS is adversary-centric
   (what attackers do); OWASP ML is risk-centric (what goes
   wrong). The audit cites both, for different reasons.
